## Learned

- Akasha's gap compared with claude-obsidian is interrupted writes. A power loss mid-apply leaves some pages written but uncommitted, plus a stale `.akasha/lock`. Nothing is lost (git has the previous versions), but cleanup is manual.

## Decisions (morning)

- Git-based undo (ADR-0003) stays; `recover` adds crash cleanup on top of it (ADR-0008 below).

## Later: built `akashactl recover`

- `.akasha/lock` now holds a JSON record, fsynced before any write: `operation`, `pid`, `host`, `started`, `paths`. `capture`, `apply` and `undo` pass the exact paths they will write. The stale-lock error now points to `akashactl recover --dry-run`.
- `scripts/lib/recover.py`, `akashactl recover [--dry-run]`. For each recorded path under `wiki/` or `.raw/`:
  - committed version exists → restore it (`git reset -- paths` unstages first);
  - not committed, not on disk but staged → unstage;
  - uncommitted complete raw copy (sha256 matches the name) → keep;
  - anything else → delete.

  Then it clears the lock. It refuses if the pid is alive on this host, if the lock is from another host, or if git's `index.lock` exists. Unsafe paths in the record are ignored.
- `tests/test_recover.py`: 18 tests. The crash tests run a real capture/apply/undo in a child process with `commit_paths` replaced by `os._exit(9)`, either before `git add` or after it, so the lock is genuinely left behind. After recover: the vault matches the pre-crash snapshot, `git status` is clean, and a second capture works (`6 new, 1 duplicate`). `python3 -m pytest` → `305 passed in 16.57s`.
- CLI run after a crashed apply: capture blocked (exit 2) → `recover --dry-run` listed 3 restores and 1 delete → `recover` → `git status` clean → second recover: "nothing to recover".
- All 18 recover tests passed on the first run; the existing 287 needed no changes.

## Decisions

- [ADR-0008](../docs/decisions/0008-recover-interrupted-writes.md): the lock is a paths-only intent record, and recover acts only on those paths. Complete raw copies are kept, nothing recovers automatically, and recover refuses when a writer is alive or the lock is from another computer.
